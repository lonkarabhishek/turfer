# TapTurf - Next.js App

## What is this?
TapTurf (tapturf.in) is a turf directory + sports games platform for every city across India that has active turfs (88 on 26 Oct 2026; started in Nashik; biggest markets Hyderabad, Bangalore, Pune, Mumbai, Delhi). Never hardcode a city count or a city list: the live list and every count come from the `city_turf_counts` view via `lib/queries/cities.ts` (getLiveCities, getFooterCities, getCityCopy), and a city the data team adds shows up without a code change. `lib/city.ts` CITIES is the curated, biggest-first list of labels, states, centroids (CITY_COORDS) and other names (CITY_ALIASES); curate a new city there so IP/GPS detection and Ask know it. Copy and lists order cities by size, except "other cities" lists in a city view (/turfs, the city home, /<city>, /<city>/<sport>), which go nearest first: a city's point is its CITY_COORDS centroid, else the median of its turfs from city_turf_counts (lat, lng; `lib/city.ts` cityPoint), and detection still uses CITY_COORDS only. This is the Next.js 16 App Router migration of the original Vite React SPA at `../src/`.

## Tech Stack
- **Framework**: Next.js 16 App Router with Turbopack
- **Styling**: Tailwind CSS v4 (CSS-based `@theme inline` in globals.css, NOT tailwind.config.ts)
- **Database**: Supabase PostgreSQL at `hwfsbpzercuoshodmnuf.supabase.co`
- **Auth**: Firebase Phone OTP + Google OAuth via Supabase
- **Deployment**: Vercel (root directory set to `tapturf-next`)
- **Images**: Google Drive URLs with native `<img>` tags + `referrerPolicy="no-referrer"`

## Design System
Airbnb-inspired: clean whitespace, `rounded-2xl` cards, `shadow-elevated`, frosted glass header (`backdrop-blur-sm`), pill-shaped buttons, `section-divider` class for content separation. Primary: `#00A699`, Accent: `#FF385C`.

## Architecture

### Pages (66 total)
- `/` — Home page (ISR, an hour; purged by list posts and the games key)
- `/turfs` — Turf listing: the server renders the first 10 cards; search, sport chips, sorts and "Show more" (10, 20, 40, 80 at a time) fetch batches from `GET /api/turfs/list`, ranked by the same code (`lib/turfList/query.ts`, tests: `npm run test:list`). Every turf in scope is a plain A to Z link at the bottom. The same list (`components/search/TurfListingClient.tsx`) is the "Popular in <city>" list on `/<city>` (Top rated is its default sort) and the list on `/<city>/<sport>` (that page's turfs by its exact labels, `pageSport`, no chips; its 24 server cards as before, by rating with no trending lead, as its copy says). Its Filters sheet (`FilterSheet.tsx`: Free hours marked (below, Free slots), Open now in India time, Open 24 hours, Floodlights, Covered, Parking, Washroom, Changing room, 4.5+ on Google, Coaching, Equipment, Claimed by owner (`f=claimed`, from the card column `turfs.claimed`, so "Nearest first" with it is claimed turfs near me), price per hour up to, surface) is ranked and counted in `rankTurfs` from each turf's facts (counts only on a first batch asked with `counts=1`, while the sheet is open, so other batches stay time-free and shared; `lib/turfList/facts.ts`: a column or its amenity words; opening_hours, coaching and surface from an hourly cached read, `lib/queries/listFacts.ts`); its choices are `f`, `price` and `surface` in the page URL, which stays the same static page with the plain canonical.
- `/turf/[id]` — 49 individual turf pages (SSG with `generateStaticParams`)
- `/sport/[sport]` — sport pages from `lib/sports.ts` (football, box-cricket, cricket, badminton, pickleball, volleyball, basketball, tennis); exact label match, add new sports there. `venue` says turf or court (racquet/ball-court sports are "courts" in all copy)
- `/games` — Games listing with sport/skill filters
- `/game/[id]` — Game detail with join request flow, the players bar, the host's updates and the activity log, at its readable URL `/game/<words>-<code>` (the folder's param is still `id`; SEO & Metadata below)
- `/game/create` — 4-step game creation wizard (protected)
- `/dashboard` — User dashboard (the Me section) with tabs, in this order: Games, Requests, Matches (everything of theirs from the free tools), Alerts (its key is `notifications`), Profile, and Passport (numbers, weekly streak, medals, stamps, reviewed turfs, played with; `lib/profile/`, `GET /api/me/passport`, tests: `npm run test:profile`), which is a pill on a wide screen only: a phone's row is the first five and the Me card opens the Passport. The tabs, their order and their `?tab=` keys are `lib/dashboard/tabs.ts` (tests: `npm run test:matches`); other pages link to tabs by key, so never rename one (protected)
- `/api/auth/callback` — Supabase OAuth callback

### Auth Flow
- **Phone OTP**: Firebase sends SMS → verify OTP → check/create user in Supabase `users` table → store in localStorage
- **Google**: Supabase `signInWithOAuth` → callback route → `onAuthStateChange` picks it up → ensure user in DB
- **AuthProvider** wraps entire app via `AuthWrapper` in layout.tsx
- **Protected routes**: `/game/create` and `/dashboard` redirect to login if not authenticated

## Important Conventions
- Mobile-first (70%+ mobile traffic). Bottom nav on mobile, footer hidden on mobile.
- Use `section-divider` class for content separation (not `<hr>`)
- Google Drive images: always use native `<img>` with `referrerPolicy="no-referrer"` and `onError` fallback
- Supabase turfs table uses `"Gmap Embed link"` (with quotes, capital G, spaces) as column name
- Game queries fetch turfs separately (no JOINs) to avoid RLS issues
- Dual auth: localStorage for phone users, Supabase session for Google users
- Games, join requests and notifications are written (and requests and notifications read) only through the games routes as the verified caller (`lib/games/server.ts`, API in `lib/games/types.ts`, tests: `npm run test:games`), except a claim decision's notice, written by `admin_answer_owner_claim` from `/api/admin/owner-claims`; the database lets the browser read only games and lineups (`supabase/migrations/20261030_games_lockdown*.sql`)
- Repeat games: the host picks a calendar-style repeat in the create flow (weekly on chosen days every 1 to 4 weeks, counted from the first game's week, or monthly on the date or the nth weekday; ending never (a year at most), on a date or after N). A series lives in `private.game_series`; its games are ordinary games with `games.series_id`, put up 4 weeks ahead (at most 8 not played, always the next one; a cancelled one doesn't count) at once and by a daily job, through `/api/game-series` (`supabase/migrations/20261102_game_series.sql`). `lib/games/repeat.ts` has the same maths for the preview; both are checked against `lib/games/repeat.cases.json` (`npm run test:games`, `scripts/sql-tests/game_series.check.mjs`). Players join each game on its own; the host books the turf for each date. /games and a turf's game list show each repeat once, its soonest game (`lib/utils/game.ts` oneGamePerRepeat); its page lists the next ones
- Already confirmed (the site owner's ask, 17 Nov 2026; `supabase/migrations/20261117_game_confirmed.sql`, applied 17 Nov; tagged players changed the next day by `20261118_game_tags_shown.sql`, see "Tagged players show at once" below; tests: `npm run test:games`, `scripts/sql-tests/game_confirmed.check.mjs`, `game_tags_shown.check.mjs`): a host can say who is in before anyone joins on TapTurf, in the create flow's Squad step and in the game's edit sheet (`components/game/ConfirmedField.tsx`, one section in both; rules, limits and words in `lib/games/confirmed.ts`, run against `lib/games/confirmed.cases.json` by the tests and the PGlite check). Three kinds, each taking a spot at once: names the host typed (`games.confirmed_names`, up to 20, 1 to 20 characters, letters of Latin, Arabic and India's scripts with spaces and . - ' only, no digit of any script so no phone number reaches a public page, no link), people without a name (`games.confirmed_extra`, 0 to 30) and tagged TapTurf players (`private.game_tags`, picked from the same field: it searches the host's Played with people first, then `players_search`, so only people with "Let others find and tag me" on; never the host or someone already in). `games.current_players` is the joined players (the host among them) plus all three, recounted by `private.game_in` wherever it used to be counted from `game_participants` alone (`game_create`, `game_update`, `game_request_send`, `game_request_answer`, the series' fill, an email's players), so every card, list, JSON-LD capacity, share card and email reads one number and a game is full exactly as before; max players can't go under everyone in (`too_few`) and confirmed people can't pass it (`bad`, field `confirmed`). Names show on the game page only (`components/game/detail/GameLineup.tsx`, "Confirmed with <host>": plain dashed chips, no photo or tick, then "+N more"); list rows drop them (`cardGame`, `shapeGames`, Ask's games: they keep only how many there were, `confirmed_named`, for the bar's speed), and they are never in JSON-LD, emails or the share card. They are not accounts: nothing about them reaches Passport, played-with, medals, reviews, emails or notifications. A tagged player gets one in-app notification (`game_tagged`; no email, no SMS; web push sends it like any notification with a game) and answers from the notification (`components/dashboard/NotificationsList.tsx`) or the card on the game page, through `GET`/`POST /api/games/<id>/tags` (`game_tags_for`, `game_tag_answer`). The public row has a count (`games.confirmed_tagged`). Yes makes them a player like any other (a `game_participants` row; the count stays, the tag held the spot), no frees the spot and that host can't tag them on that game again, the host can untag (`confirmed_untag` in the edit); a called-off game ends its tags (job `game-tags-expire`, every 10 minutes). As 20261117 alone has it (and for any tag made before 20261118, `private.game_tags.shown` false): "Asha added you as confirmed for ...", titled "Are you in?", "Yes, I'm in" or "Not me"; until yes only the host is sent who is tagged and the page says "+1 more"; a tag nobody answered ends when the game starts. The host hears each answer in the app (`game_tag_yes`, `game_tag_no`). Limits in SQL: 20 waiting tags a game, 50 tag notifications a host a day, one player told about one game 3 times at most. Repeats: the names and the count are kept on `private.game_series` and copied onto every game it puts up; tags are for the first game only (a repeat would notify the same people for every game); an edit changes that one game. No foreign key to `public.users`: on an account erasure, clear its `private.game_tags` rows (`user_id` or `host_id`) by hand with its other rows (a tag whose account is gone is skipped by every read and count meanwhile). Before the file is applied the section is not shown (the create flow asks whether games have `confirmed_names`, the edit sheet looks at the row) and the routes refuse the keys plainly (`confirmed_off`); every other create and edit is the body it always was. `lib/games/legacy.ts` (the fallback from before the game functions) knows none of this. Also for people who dont have usernames, assign them one"; `supabase/migrations/20261128_usernames_assigned.sql`, applied 28 Nov (425 accounts given one, 10 of them turferN); `scripts/sql-tests/usernames_assigned.check.mjs`; tests: `npm run test:account`, `test:my`, `test:consent`). The rule: nobody becomes findable, taggable or publicly visible because TapTurf gave them a username; a profile goes public only by the person's own tap. So a given username is NOT a `public.usernames` row. It waits in `private.username_assigned` (one row per account, ever: `username`, `source` backfill or signin, `chosen_at` null while it waits, `chosen_how` kept, changed, own or off), which no public function reads, so every reader of `public.usernames` (the profile page, player search, tagging, the medal badge, "Managed by", a tournament's organiser, live tags, the admin's lists) sees an account with no username, exactly as before. Never put a given name in `public.usernames` yourself: `private.account_is_empty` counts any row there as a used account (adding Google over a Google account's own empty row would be refused for everyone), `usernames_mark_managed_turfs` fires on every insert there, and `private.profile_json` would hand it to every screen as if picked. The name is made from the name on the account and nothing else (`private.username_from_name`; `lib/account/assigned.ts` has the same rule and every word people read; both run against `lib/account/assigned.cases.json`): letters only, accents folded, a leading title left out, `first_last` when that is 16 characters or fewer, else the first word and the last word's initial, else the first word cut at 16; then the first free of base, base2, base3, ... (free: nobody has it, had it, or is waiting to choose it); a name with no usable letters (other scripts, emoji, only digits), under 3 letters, a reserved word, an email address, or the part of one of the account's own addresses before the @ gets turfer1, turfer2, .... No digit of a name is kept and the phone number is never read, so nothing of a number or an address can come through. Three server-key functions, none replacing an earlier one: `username_ensure` (the name waiting for an account, given now if it has none: a new account gets its name at its first signed-in request, from `postMe` after the reply and `GET /api/account/username?suggest=1`), `username_choose` (every username write: Keep it is a null name; a name waiting for someone else is taken; otherwise it calls `public.username_set` as it is, so a first username is free of the 3 changes in 30 days and public unless the switch was turned off first; a given name someone changes away from is free again and never goes to `username_history`) and `username_check_all` (the live check). `lib/account/server.ts` falls back to `username_set` and `username_check` when they are not there (or their execute is revoked, the file's way to switch it off), so the app works before the file: nobody is given a name and the sheet asks as before. What people see (`components/account/AssignedUsernameCard.tsx`, `useAssignedUsername.ts`): "Your username is @asha_rao", Keep it and Change, one line under them, and Not now (7 days on that device, `tapturf_username_card_v1`; never a dialog), on the Me card where "Pick a username" was and at the top of the Profile section when that is open; Change puts the cursor in the Profile section's own username box, prefilled, with the live check; turning the switch on there with the given name still in the box is keeping it. The given name is held in memory only, never in the stored profile, and `UsernamePrompt` (the sheet) never opens for an account that has one. The backfill wrote one in-app notice each (`username_assigned`, linked to `/dashboard?tab=profile#username` by `lib/my/claimNotice.ts`): no email (`private.email_kind_of` knows no such type) and no push (each notice is claimed in `private.push_sends` first, so the dispatch finds nothing to send). No foreign key: on an account erasure clear its `private.username_assigned` row by hand. The privacy page says it under "Your username and public profile"; no new site-wide notice.

## SEO & Metadata
- Titles and descriptions are built from each page's own data in `lib/seo/`: `turfMeta.ts` (turf pages), `listingMeta.ts` (home, city, city+sport, sport, near-me), `blogMeta.ts` (posts, with optional `seoTitle`/`seoDescription`; `npm run check:blog` checks them), `pageMetadata.ts` (home, /turfs, /games). Titles fit 60 characters and about 580px (`width.ts`), descriptions 155 characters. Shared robots/OG/Twitter pieces are in `defaults.ts`. Tests: `npm run test:seo`.
- Honest snippets: no booking claims (players call or WhatsApp the turf), no invented numbers or urgency. Google ratings may appear in visible text as "on Google", never in structured data. One exception, the site owner's call (4 Nov 2026): the /pune title alone reads "Turf Booking in Pune: N Turfs, Call or WhatsApp" (`BOOKING_TITLE_CITY` in `lib/seo/listingMeta.ts`); BANNED_COPY still holds everywhere else. Where people need to know how to book, the site owner's wording (5 Nov 2026) is "For bookings, contact the turf directly." (the venue, for a typed venue); never "TapTurf doesn't take bookings" or "we don't take bookings" in anything a person sees.
- City pages with fewer than 3 active turfs (`MIN_TURFS_TO_INDEX`) are `noindex, follow` and out of the sitemap (`cityPageIndexable` in `lib/queries/cities.ts`), as thin city+sport pages already were; they stay linked so their turfs are reachable, and a city becomes indexable again by itself at 3 turfs.
- Errors: `pages/500.tsx` is the static branded 500 page (noindex). When a page has no copy of its data fresh enough to show (a last good copy is used for at most an hour, `lib/cache/rowStore.ts`), it throws `Unavailable` (`lib/cache/unavailable.ts`) and `pages/_error.tsx` answers 503 with Retry-After, no-store and noindex, so stale hours or prices are never shown as current and nothing thin is cached. Vercel puts `_error`, `_app` and `_document` in every function but not `pages/500.js`, so `npm run build` adds the error pages and the files their traces list to every app route's trace after `next build` (`lib/build/errorPages.ts`, tests: `npm run test:build`); `outputFileTracingIncludes` cannot (with Turbopack it matches nothing under `.next/`).
- Every `<script type="application/ld+json">` uses `jsonLdHtml` from `lib/seo/jsonLd.ts` (escapes `<`, `>`, `&`), never raw `JSON.stringify`.
- A turf's JSON-LD carries `aggregateRating` only from TapTurf players' own live reports, at `AGGREGATE_RATING_MIN_REPORTS` (5, `lib/seo/defaults.ts`) or more. Listing pages carry no ratings.
- Turf photos on Google: only photos owners added on myTapturf (`turf-photos/owner/<turf>/<24 hex>[-card].<webp|jpg>`) are served from tapturf.in (`/photos/turf/...`, `app/photos/turf/[...path]/route.ts`, `lib/utils/images.ts` sitePhotoUrl), lead og:image and the turf JSON-LD image, and go in the image sitemap. The mirror job's copies of Google Maps photos keep their Supabase links (Supabase sends `x-robots-tag: none`), the site owner's call (2 Nov 2026). Tests: `npm run test:turf`, `npm run test:seo`.
- Games' SportsEvent JSON-LD (the game page and the /games ItemList of the first 20) is built in `lib/seo/gameJsonLd.ts`: organizer is the host as a Person with url, their public profile `/u/<username>` when it is shown, else the game page (`lib/games/hostProfile.ts`: players_search for `games.host_name`, kept only when profile_owner names the game's creator, no new database function; remembered 10 min per process, none while building); performer is the host by name; image is the game's own share card. The card (`GET /api/og/game/<id>`, 1200x630, also `/4x3` and `/1x1`; what it says in `lib/og/gameCard.ts`, the designs in `lib/og/gameCardDesigns.tsx` with `CARD_DESIGN` picking the live one of three (a night turf, b match ticket, c matchday poster), each sport's pitch and ball in `lib/og/gameCardArt.tsx`) says the sport, the stored India day and time, the venue, area and city, who is in of how many as a row of dots with the spots left ("Almost full" only with 1 or 2 left in a game mostly full, "Full", "Joining closed" once played, "Cancelled"), the price each or "Free", the level, "Turf booked" when the host said so and the host's first name (never a confirmed or tagged player's), with "Join on tapturf.in" across the foot; it is the game page's og:image and twitter:image, and is drawn only in next/og's bundled Noto Sans and inline SVG (text the font lacks is left out, so it never fetches a font, emoji or picture; the rupee sign and the tick are drawn shapes, bold is a stroke since the font has one weight; capitals are made before that check, never with textTransform, and a long word shrinks its line or wraps, never runs off the card). Its URL carries `?v=` (a hash of what it says and of its design): a current URL is kept a day, any other 307s to the current one. Tests: `npm run test:seo`, `npm run test:games`.
- `/turf/<uuid>` (the turf URLs before 19 Oct) answers 308 to `/turf/<slug>` from the proxy (`proxy.ts`, `lib/turfIds.ts`), a Map lookup with no database read, query string kept: `npm run build` writes every active turf's id and slug from the build-data step's sitemap read into `lib/turfIds.json` before `next build` bundles it, then puts the committed `{}` back (`lib/build/turfIds.ts`; tests: `npm run test:build`). Anything not in the map (no slug, inactive, added since the deploy, a build with `TAPTURF_BUILD_DATA=off`) falls through to the page, whose `permanentRedirect` (`app/turf/[id]/page.tsx`) stays the fallback. The map is as of the deploy: a slug edited by hand or a turf switched off afterwards needs a redeploy, or its id link 308s to the old slug (a 404). The build log prints the map's md5, which equals `select md5(string_agg(id::text || ',' || slug, E'\n' order by id)) from public.turfs where is_active and slug is not null` while the map is current. Links, share text and JSON-LD use the slug (`lib/utils/turfPath.ts`), never the id.
- A game's page is `/game/<words>-<code>` (`lib/utils/gamePath.ts`, tests: `npm run test:game`), e.g. `/game/football-dn-parande-dhanori-pune-sat-15-nov-7pm-4b63fb76`: the sport, the venue's name (its turf's or the typed one), area and city, the stored India day and start time, lower-case ascii, then the first 8 hex characters of the game's id. No column and no migration: the page finds the game by the code alone (a range on the primary key, `getGameByParam` in `lib/queries/games.server.ts`), so the words are free to change. `/game/<uuid>`, a bare code and words that are out of date (the venue, day or time was edited) answer 308 to the current URL from the page (`permanentRedirect` in `app/game/[id]/page.tsx`, an ISR entry like the page, purged by the games tag); the redirect drops a query string (the proxy makes no network call for it). Two games sharing a code (none on 12 Nov 2026) each live at `/game/<words>-<uuid>`, and a short link goes to the one whose words it has (`resolveGameParam`). Canonical, og:url, JSON-LD `@id`/`url`, the sitemap, share text, cards and emails (`lib/email/templates.ts` pagePath, from the job's own game; the database still sends `/game/<uuid>`) use `gamePath`/`gameUrl`, never `/game/${id}` by hand; a caller with only the id (a notification, a push, a request row, the admin) passes `{ id }` and gets the id link, which redirects. Only the page URL changed: API routes, `/api/og/game/<id>`, tournaments' `gameTournamentCode` and `/tools/turf-session?game=<id>` keep the id. An unknown code renders "Game not found" (200, noindex), as an unknown id always did.
- All-India listing pages stay small (Googlebot reads the first 2 MB of HTML): `/sport/<sport>` shows its top 24 venues as cards, then "<Sport> turfs by city" (`lib/byCity.ts`, `components/sport/ByCityLinks.tsx`): `/<city>/<sport>` where that page is indexable (`MIN_TURFS_TO_INDEX`), else `/<city>` when that has as many turfs, else "and N more cities". `/turf-near-me` shows the six biggest cities' top 8 as cards and links every live city's page, one turf or more (a city with fewer than 3 turfs is noindex, follow and out of the sitemap, `cityPageIndexable` in `lib/queries/cities.ts`, but stays linked so players and crawlers reach its turfs); its JSON-LD ItemList lists only the cards. ## Commits & Deploys
- Batch the work: commit to the working branch as you go, but merge into `main` (which deploys to production) once per batch, not after every commit.
- At most one production deploy a day (site owner, 4 Nov 2026): each deploy empties the page cache, and the refill strains the database. Exceptions ship right away, still with the usual checks: security fixes and bugs that break production.
- Pushing the working branch only makes a Vercel preview; only `main` goes live. `claude/**` branches make no deployment at all (`vercel.json` git.deploymentEnabled).
- Page timers and purges (10 Nov 2026): turf pages a week, city, city+sport, all-India list pages and the sitemap a day, the home and its `/c/<city>` twin an hour, games pages 10 minutes, each purged within about a minute (lists: the list gap) by the cache queue's keys through `/api/revalidate` (`lib/cache/keys.ts` purgeCalls): `turf:<key>` its page, `list:<city>` the tags `turf-data:<city>` and `turf-data:india` (and the old `turf-data`), `games` the `games` tag. A list page names its scope before its first turf read (`setListScope(city | INDIA)`, `lib/queries/listScope.ts`); without one it reads the hour-long shared entries and carries the old tag, so every city's post refreshes it. A shared `unstable_cache` entry a page reads lowers the page's revalidate to its own: what turf pages read lasts a week (`lib/cache/revalidate.test.ts` pins the timers, `npm run test:cache`). Turf pages and scoped list pages prerendered at a deploy keep a 15 to 30 minute first life (`lib/queries/firstLife.ts`: a purge sent during the build reached the old deployment only). Pages that list open games are kept no longer than just past the next game's kickoff + 30 minutes (`lib/queries/changeMark.ts`; nothing writes to the database then), never more often than their old timers. A `/c/<city>` twin showing a nearby city's turfs also carries that city's tag (`tagShownList`).
- What a follower costs (the site owner, 23 Nov 2026: "serve them but not cost a lot"): a live scorecard or tournament page asks for the score on a timer, and every ask is a billed request whether the CDN or a function answers it, so the timers are the cost. A live scorecard asks every 10 s (`LIVE_POLL_MS`, it was 6), every 20 s once the score has not moved for 2 minutes (`LIVE_QUIET_POLL_MS`), every 30 s for 30 minutes after the end, never while the tab is hidden; a failed ask is retried no sooner than a good one (`FAIL_BACKOFF_MS`). A tournament page asks every 15 s with a match live, else every 60 s (`TOURNAMENT_LIVE_POLL_MS`, `TOURNAMENT_POLL_MS`; they were 10 and 30). The CDN keeps each answer a few seconds (`LIVE_CDN_FRESH_S` 4 + `LIVE_CDN_STALE_S` 5; `TOURNAMENT_CDN_FRESH_S` 5 + `TOURNAMENT_CDN_STALE_S` 8), so many followers of one match share one function run; fresh plus stale must stay under the poll (tests pin it), or a match with one follower is handed the copy its own last ask made and runs a whole poll behind. The scorer's own sends (`LIVE_SEND_EVERY_MS`) are untouched. Tests: `npm run test:live`, `test:tournament`.

## Build & Run
```bash
npm run dev          # Dev server (Turbopack)
npm run build        # Production build: the build-data step, then next build
npx next start -p 3005  # Production server
```
`npm run build` (what Vercel runs) first reads every row the prerendered pages share, once, patiently (`scripts/build-data.ts`, waits out a slow database for up to 6 min, else fails and production keeps the last deploy), and `next build` prerenders from those files: page generation reads nothing from the database (`lib/build/data.ts`). A new shared read a prerendered page makes needs a hook there (`buildData`), or the build logs `build: a page read the database <path>` (`TAPTURF_BUILD_DATA_STRICT=1` makes that fail; `npm run test:build`). `TAPTURF_BUILD_DATA=off npm run build` (or `npx next build`) builds without the step, as before, e.g. with no database.
